# Заявки Tilda и приглашения по почте

Дизайн портала сохранен. В этом обновлении нет новых миграций. По просьбе владельца локальные тесты, проверка типов и сборки не запускались; изменения проверяются после сборки и установки на VPS. До получения отчета с VPS точная причина недоставленной заявки и отказа SMTP не установлена.

## Что изменилось

- CRM обновляет список и этапы каждые 15 секунд, при возвращении во вкладку и по кнопке «Обновить заявки». Во время редактирования и переноса фоновое обновление приостанавливается. Есть сброс фильтров. У суперадминистратора по-прежнему доступ ко всем заявкам; фильтра «только мои» на сервере нет.
- Если `SMTP_FROM` не указан, используется адрес `SMTP_USER` вместо `noreply@localhost`. Проверяются сочетание порта и шифрования и наличие настроек. Установлены ограничения ожидания соединения; проверка TLS-сертификатов сохранена.
- Ошибки SMTP объясняют проблему авторизации, соединения, TLS или адресов. У сотрудника больше не появляется ложное сообщение об успешной отправке, когда SMTP отказал. Созданный аккаунт и зачисление ребенка сохраняются.
- В журнале появились безопасные события `TILDA_EVENT` и `MAIL_EVENT`: результат и категория сбоя, без телефонов, ников, email, паролей и ссылок приглашений. Неотправленные письма больше не печатаются в консоль.

## Установить обновление

Используйте блок «Обновление VPS» из [CRM_ENROLLMENT_UPDATE.md](CRM_ENROLLMENT_UPDATE.md): он скачивает master, собирает backend/web, сохраняет резервную копию базы и `.env`, применяет недостающие миграции и перезапускает сервисы. GitHub сам по себе не обновляет работающие контейнеры. Не показывайте `docker compose config` без `--quiet`: полный вывод содержит секреты.

## Получить отчет на VPS

После установки новой версии, повторной отправки тестовой формы и попытки приглашения:

```bash
cd /opt/globoatlas
bash scripts/diagnose-integrations.sh
```

Отчет содержит версию файлов, состояние контейнеров, количество заявок, даты пяти последних заявок Tilda, HTTP-статусы последних обращений к Webhook, последние миграции и результат соединения с SMTP. Проверка SMTP выполняет соединение, TLS и авторизацию, но не отправляет письмо. Успешная авторизация сама по себе не гарантирует разрешение отправителя и доставку в почтовый ящик. Тайм-аут отчета — 45 секунд.

Отчет и выбранные события можно прислать для диагностики: значения токенов, SMTP-пароль, адреса получателей и содержимое писем туда не выводятся. Сам `.env` присылать не нужно. Скрипт требует уже обновленный контейнер backend; ошибка отсутствия `dist/src/mail/smtp` означает, что запущен старый образ.

## Как читать результат

| Результат | Следующее действие |
| --- | --- |
| `crmEnabled: false` | Включить `CRM_ENABLED=true` и пересоздать backend |
| `tildaTokenConfigured: false` / HTTP 401 | Сверить `TILDA_WEBHOOK_TOKEN` на VPS и `Authorization: Bearer …` в Tilda |
| HTTP 400 / `phase: fields` | Проверить переменные формы и непустой контакт в заявке Tilda |
| `phase: validation` | Проверить обязательные данные формы, в том числе имя родителя |
| `phase: database`, `P2021` / `P2022` | Проверить применение миграций и согласованность образов |
| HTTP 200 / `delivery_saved` | Заявка сохранена либо это повторная доставка; открыть CRM, сбросить фильтры, посмотреть «Все заявки» |
| Новых обращений к Webhook нет | Проверить журнал заявки в Tilda, подключение Webhook к конкретному блоку и публикацию страницы; запрос также мог не дойти до backend |
| `SMTP_AUTH` | Проверить полный email, пароль приложения Почты и разрешение почтовых клиентов в Яндексе |
| `SMTP_CONNECTION` | Проверить адрес/порт SMTP и исходящие подключения у провайдера VPS; это не подтверждает, что пароль неверен |
| `SMTP_TLS` | Проверить шифрование, адрес сервера и дату VPS; не отключать проверку сертификатов |
| `SMTP_ADDRESS` | Проверить получателя и принадлежность адреса SMTP_FROM отправителю |
| `SMTP_TEMPORARY` / `SMTP_REJECTED` | Проверить ограничения почтового ящика и повторить позже |

## Яндекс

Редактирование выполняется только на VPS:

```bash
cd /opt/globoatlas
nano .env
```

Нужные настройки (замените примеры своим ящиком и паролем приложения):

```dotenv
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=ваш_ящик@yandex.ru
SMTP_PASS=пароль_приложения_Почты
SMTP_FROM="ГлобоАтлас <ваш_ящик@yandex.ru>"
```

Пароль приложения создается для того же Яндекс-аккаунта, который указан в SMTP_USER. В настройках Яндекс Почты должен быть разрешен доступ почтовых клиентов. Если SMTP_FROM содержит другой адрес, Яндекс должен разрешать отправку от его имени. [Настройка почтовой программы](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others), [ошибки авторизации и отправителя](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/mail-clients-troubleshooting).

После изменения `.env` нужен новый контейнер, обычный `restart` не перечитывает переменные Compose:

```bash
cd /opt/globoatlas
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate --no-deps --wait --wait-timeout 240 backend
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate --no-deps --wait --wait-timeout 120 nginx
bash scripts/diagnose-integrations.sh
```

Для повторной отправки сотруднику используйте существующую карточку, а не создавайте дубль аккаунта. Действующая кнопка повторного приглашения сотрудника сбрасывает старый пароль: интерфейс об этом предупреждает. В CRM повторная отправка приглашения не зачисляет ребенка еще раз.

Параметры TLS и тайм-аутов сверены с [документацией Nodemailer](https://nodemailer.com/smtp).
