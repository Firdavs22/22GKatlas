# Tilda, документы при зачислении и канбан

Обновление от 16 сентября 2026 года. Для запуска нужны новые образы backend/web и миграция `20260916030000_admission_document_checklist` (тринадцатая). Она добавляет необязательные JSON-поля к заявке и зачислению. Существующие данные сохраняются. Новые переменные `.env` не нужны; действующие настройки SMTP и `TILDA_WEBHOOK_TOKEN` остаются прежними.

## Ошибка на скриншоте

HTTP 400 с текстом «Укажите телефон или контакт выбранного мессенджера» возникает при приеме формы Tilda, до зачисления. Опубликованная форма отправляет стандартные `messenger-type` и `messenger-id`; предыдущий обработчик ожидал `contactMethod` и `contactValue`/`Phone`. Теперь принимаются оба варианта. `max_messenger` преобразуется в Max. Для Telegram, VK и Max допустим ник, ссылка или телефон; для способа «Телефон» нужен номер +7/8.

Фактические поля опубликованной формы на `globokids.ru` проверены без отправки заявки:

| Поле | Переменная | Результат в CRM |
| --- | --- | --- |
| Имя родителя | `Name` / `name` | Имя родителя |
| Возраст ребенка | `Input` / `input` | Исходный возраст |
| Способ связи | `messenger-type` | Телефон, Telegram, VK, Max |
| Контакт | `messenger-id` | Телефон или контакт мессенджера |
| Дата посещения | `Date` | Желаемая дата посещения |
| Согласие на обработку данных | `Checkbox` | Отдельный ответ формы |
| Согласие на рекламу | `Checkbox_2` / `Checkbox 2` | Отдельный ответ формы |

Регистр не важен. Смысл общих полей `Input` и `Checkbox` подтвержден для форм `form908246677` и `form1000686846`; только у этих форм они сопоставляются автоматически. `formid` присылает Tilda. Также поддерживаются явные подписи `ВОЗРАСТ РЕБЕНКА` и `ДАТА ПОСЕЩЕНИЯ`. Для новых или скопированных форм лучше назначить `childAge`, `dataConsent`, `marketingConsent`: это исключает зависимость от ID блока. Незаполненные/непереданные согласия остаются неизвестными, а не положительными. Возраст не превращается в дату рождения, посещение не назначает дату начала обучения.

Webhook: `https://lk.globokids.ru/api/crm/tilda`, метод ключа HEADER, имя `Authorization`, значение `Bearer ` и прежний секрет. Дополнительные опции товаров и «только после оплаты» для заявки не нужны. Cookies нужны только при передаче UTM через TILDAUTM; сырые cookies не сохраняются. JSON и обычные POST-поля поддерживаются.

Повторная доставка одного `tranid` не создает новую заявку. Две самостоятельные отправки формы имеют разные `tranid` и могут создать две заявки одной семьи: автоматически объединять разных детей по общему телефону нельзя. Выбор мессенджера сохраняет контакт, но сам по себе не подключает переписку или АТС.

После обновления отправьте новую тестовую заявку. Данные старой неудачной доставки автоматически из Tilda не восстанавливаются. При изменении настроек подключения привяжите Webhook к нужному блоку и опубликуйте страницу заново — [инструкция Tilda](https://help-ru.tilda.cc/forms/webhook).

## Документы при зачислении

В CRM откройте заявку → «Зачислить»:

- Основные пункты: подписанный договор, паспорт родителя/законного представителя, свидетельство о рождении, медицинские справки.
- По необходимости: согласие на обработку данных и разрешение на получение ребенка представителями.
- Можно добавить свои пункты, указать обязательность и примечание/срок. До 30 документов с учетом основных.
- Отметки можно сохранить кнопкой «Сохранить чек-лист без зачисления». Черновик сохраняется в заявке, редактирование защищено номером версии.
- Если обязательные документы отсутствуют, система показывает список. Зачисление разрешается после комментария администрации длиной от 10 символов, например со сроком предоставления. Это правило проверяется и на сервере.
- Телефон и имя родителя можно дополнить прямо в окне зачисления. Для нового аккаунта родителя по-прежнему нужен email; также можно выбрать существующего родителя.

При зачислении сохраняются снимок чек-листа, недостающее, автор и дата. Причина неполного комплекта входит в историю заявки. Снимок доступен в папке ребенка администрации и его связанным родителям. У педагогов и других родителей доступа нет. Это сведения на дату зачисления; последующая загрузка файлов не меняет отметки автоматически. Файлы прикладываются в закрытой папке ребенка после зачисления.

Повторное нажатие «Зачислить» возвращает существующее зачисление. Создание ребенка, связь с родителем, группа и снимок документов сохраняются в одной транзакции. Проверки дат, аккаунта, дубля ребенка и свободного места сохранены. Основное назначение групп в портале продолжает работать независимо от включения CRM.

## Канбан

Карточки получили цветные заголовки этапов, более четкую структуру контактов и задач, ответственного и счетчики. Перенос — за значок с точками в правом верхнем углу карточки. Есть подсветка принимающего этапа, движущаяся карточка и анимация соседних карточек. Для клавиатуры: фокус на значке, пробел, стрелки влево/вправо, пробел для подтверждения; Escape отменяет. Можно выбрать этап в нижнем списке карточки, в том числе на телефоне.

Перенос отображается сразу и сохраняется на сервере. При ошибке восстанавливается прежнее положение и запрашивается актуальная карточка; конфликт версии не перезаписывает чужое изменение. После успешного переноса доступно «Вернуть обратно». Это обычный обратный переход с записью в истории. Учитывается системная настройка уменьшения анимации.

## Обновление VPS

Выполните блок целиком в SSH. Образы собираются при работающем портале; затем будет короткий перерыв на резервную копию, миграцию и перезапуск. Команды не удаляют базу и не создают тестовых пользователей. При ошибке блок останавливается: сохраните вывод, не запускайте `migrate reset`, `down -v` или `git reset --hard`.

```bash
bash <<'UPDATE'
set -euo pipefail
cd /opt/globoatlas
dcp() { docker compose -f docker-compose.yml -f docker-compose.prod.yml "$@"; }
git pull --ff-only origin master
dcp config --quiet
dcp build backend
dcp build web
umask 077
release_backup="/opt/globoatlas-backups/update-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$release_backup"
cp .env "$release_backup/env"
dcp stop backend web
dcp exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' </dev/null > "$release_backup/database.dump"
test -s "$release_backup/database.dump"
dcp exec -T postgres pg_restore --list < "$release_backup/database.dump" >/dev/null
dcp run --rm -T --no-deps backend npx --no-install prisma migrate deploy </dev/null
dcp up -d --wait --wait-timeout 240 backend web
dcp up -d --force-recreate --no-deps --wait --wait-timeout 120 nginx
dcp exec -T nginx nginx -t </dev/null
dcp ps
printf '\nОбновление завершено. Резервная копия: %s\n' "$release_backup"
UPDATE
```

Этот архив содержит базу и `.env`; он не заменяет резервную копию файлов хранилища. В GitHub секреты не отправляются.

## Что проверено

Production-сборки backend/web, 72 модульных теста и 9 проверок папки/файлов ребенка прошли. Проверены стандартные поля Tilda, отдельные согласия, защита повторов, черновик документов и конфликт версии, блокировка зачисления без документов/комментария, снимок при зачислении и закрытый доступ. В браузере на вымышленных данных проверены перенос мышью в пустой этап, перенос клавиатурой, Escape, выбор этапа из списка, добавление документа и разблокировка по комментарию; проверена верстка на ширине 390 px. Временная страница предпросмотра удалена из проекта.

Миграция PostgreSQL и вся цепочка с настоящими Tilda/SMTP на VPS локально не запускались. После обновления проверьте: новую заявку с сайта; сохранение контакта, возраста и даты; перенос и сохранение после обновления страницы; чек-лист без комментария и с ним; появление ребенка в группе и снимка документов; отправку приглашения; вход родителя и доступ к его ребенку. Предоставление приглашения выполняется отдельной кнопкой и не отменяет зачисление при ошибке SMTP.
